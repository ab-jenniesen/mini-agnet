# 执行阶段的节点结构草案

整理日期：2026-10-23。状态：建议，待确认；尚未实现。

## 1. 范围与前提

本文讨论用户可配置的执行子工作流中的节点。外层清单生成、交付完整性检查和结果处理继续由内核安排，当前不增加模型内容验收。

建议采用显式输入输出映射，由框架读取和更新工作流状态。该方案尚未由用户确认。

节点分为三种对象：

| 对象           | 职责                                                     |
| -------------- | -------------------------------------------------------- |
| NodeDefinition | 用户保存的静态配置，描述节点执行什么、输入来源和输出位置 |
| NodeExecutor   | 注册到框架的执行器，实现某种节点能力                     |
| NodeRun        | 一次实际执行的记录，由运行时创建并管理                   |

## 2. NodeDefinition：配置示意

以下字段名、引用路径和工具名仅为设计示意，不是当前运行时支持的配置。

```json
{
  "id": "write_docs",
  "type": "agent",
  "name": "编写交付文档",
  "inputs": {
    "goal": { "from": "task.goal" },
    "deliverables": { "from": "task.deliverables" },
    "materials": { "from": "state.materials" }
  },
  "config": {
    "instructions": "根据目标和资料生成要求的交付文件。",
    "modelRef": "default",
    "toolRefs": ["read_file", "write_file"]
  },
  "outputs": {
    "artifacts": { "to": "state.artifacts" }
  }
}
```

| 字段    | 作用                           | 建议约束                              |
| ------- | ------------------------------ | ------------------------------------- |
| id      | 工作流中引用节点的身份         | 在该工作流定义内唯一                  |
| type    | 选择已注册执行器               | 如 agent、model、tool，执行器必须存在 |
| name    | UI 中的可读名称                | 可选，不参与节点身份判断              |
| inputs  | 把来源数据绑定到执行器输入字段 | 映射后根据执行器的输入约束校验        |
| config  | 该类型的静态参数               | 根据执行器的配置 Schema 校验          |
| outputs | 把执行器输出字段写入工作流状态 | 检查字段、类型和目标写入范围          |

最低必要信息包括节点身份与执行器类型；输入、配置和输出按类型定义必需项，允许无参数节点使用空对象。

### 输入与输出的命名空间

- `task.*`：内核提供的只读任务数据，例如目标和生效交付清单。
- `state.*`：执行子工作流的可更新业务状态，例如已收集资料、产物引用。
- 执行器只收到映射完成的输入对象，普通业务逻辑不直接修改全部状态。
- 输出映射只写入允许的工作流状态范围，不能覆盖内核任务状态、权限、交付清单或验收结论。

引用语法由框架解析。首版建议采用受限字段路径，固定值另用明确的 value 绑定，不在配置中执行任意 JavaScript。缺失的必需路径报错；可选字段和默认值规则另行设计。

共享状态的数据结构及合并规则由工作流统一声明。并行节点写入相同字段时，框架按该字段的规则处理；没有明确规则时报告冲突。

### Agent 参数说明

- instructions 提供节点的角色和任务方法，不能覆盖内核策略。
- modelRef 引用宿主中已配置的模型设置。
- toolRefs 声明希望使用的工具，实际可调用范围受用户授权与宿主策略限制。
- 模型凭据、工具实现、进程句柄和事件回调由运行时注入，不保存在节点配置中。
- Skills、上下文策略和记忆策略可以后续通过引用或类型配置扩展，正式字段待讨论。

## 3. NodeExecutor：统一接口，类型各自实现

概念接口：

```text
execute(input, config, runtimeContext) → outcome
```

建议执行器注册时描述输入、配置和输出 Schema，并实现执行逻辑。

候选节点类型：

| type        | 作用                                            |
| ----------- | ----------------------------------------------- |
| agent       | 运行一次完整 Agent 循环，可以多次调用模型和工具 |
| model       | 完成一次模型调用，按配置返回文本或结构化结果    |
| tool        | 运行一个已注册工具                              |
| human       | 发出结构化输入请求并等待用户回复                |
| subworkflow | 执行另一个注册工作流并映射结果                  |

该列表是候选范围，第一版包含哪些类型尚未确定。条件路由优先通过工作流的边表达；未来可以按需要注册更多执行器。

runtimeContext 可提供身份、取消信号、受控模型和工具入口、上下文管理、产物登记、等待服务与事件接口。权限通过受控入口落实，不能仅凭隐藏字段假设执行器已被系统隔离。

outcome 建议区分：

- 完成：携带符合输出 Schema 的 outputs。
- 等待：携带可序列化的用户输入或审批请求，以及恢复所需的持久信息。
- 失败：携带结构化错误。

取消、重试和节点状态由运行时协调；具体协议待设计。对外等待请求不包含函数或无法通过客户端协议传输的对象。

## 4. 输出数据与控制流

建议后继、条件和汇合规则保存在工作流的 edges 中，不把所有路由规则塞进节点配置。

建议执行顺序：

1. 解析并校验输入绑定。
2. 创建 NodeRun，发出节点开始事件。
3. 执行对应 NodeExecutor。
4. 校验执行器输出。
5. 应用输出映射和状态合并规则。
6. 持久化更新、记录执行结果并调度后继。

等待或异常按对应分支处理，不能自动使用一份无效输出继续后继节点。

Agent 执行器返回的 artifacts 应关联运行时登记的文件或资源引用；最终文件是否齐全仍由外层完整性检查确认。

## 5. NodeRun：实际执行实例

建议记录：

- nodeRunId、runId、nodeId，及执行的工作流版本。
- 状态、等待原因、开始和结束时间。
- 本次输入和输出或其存储引用。
- 错误、用量、耗时和产物关联。
- 当前尝试次数及重试关联。

同一节点定义在循环或并行分发中可以有多个 NodeRun。节点重试需另外记录 attempt；NodeRun 标识与重试粒度的正式约定尚未确定。

UI 通过这些记录和事件显示进度。静态节点配置中不保存本次 status、运行 ID、耗时或当前结果。

### 与工作流 State 的区别

本文用到两个容易混淆的词：State 表示共享的业务数据，status 表示某个执行实例的进度。执行记录在广义上也属于系统状态；这里按职责区分业务数据和运行信息。

| 对象           | 回答的问题                                     | 示例                                   |
| -------------- | ---------------------------------------------- | -------------------------------------- |
| Workflow State | 当前工作流处理到什么数据，后续节点可以使用什么 | 资料列表、草稿、产物引用               |
| NodeRun        | 某次节点执行发生了什么                         | 输入、输出、错误、耗时、用量和执行身份 |
| NodeRun.status | 该执行实例处于什么阶段                         | 运行中、等待、完成或失败，正式枚举待定 |

例如 write_docs 的某次尝试因权限拒绝而失败，交付物状态保持未生成，同时执行记录保留失败及原因。用户授权后重试成功，工作流 State 更新为已有 README.md；执行记录仍保留之前的失败和后续成功，具体存为多个 NodeRun 还是同一 NodeRun 下的 attempts 仍待确认。

工作流 State 通常表达当前生效数据；检查点可以保留它的历史版本。执行记录表达执行过程与尝试，用于追踪、统计和恢复判断。两者可以引用同一份输出产物，避免重复保存大内容。

“单独保存”表示对象职责分开，不强制分成不同文件或数据库。可以放在同一运行文档的不同字段，或使用关联表。状态更新与成功记录应保持一致，具体持久化方案待设计。

恢复还需要调度位置、待执行节点和等待请求等运行状态。只保存业务 State 或一组普通执行日志，都不足以自动保证可靠恢复。

### 数据归属的建议，待确认

按 Session、Task、Run、NodeRun 分层归属：

```text
Session
├─ 会话消息及任务关联
└─ Task
   ├─ 目标、计划、交付清单、累计成果、任务状态
   └─ Run：一次推进该任务的执行
      ├─ 工作流版本与本次配置
      ├─ 工作流 State：本次执行共享的业务数据
      ├─ Run 状态、调度位置与检查点
      └─ NodeRun：某节点的执行实例
         ├─ nodeId、输入、输出或引用
         ├─ 执行状态、等待原因与错误
         └─ 开始结束时间、耗时、用量与尝试信息
```

- 工作流共享 State 建议归属于本次 Run 的工作流实例；节点读取指定输入并返回更新，框架应用到该 State。各节点不必分别保存一份完整共享 State。
- 节点实际执行信息保存在 NodeRun，由所属 Run 统一管理；它通过 nodeId 关联静态节点定义。
- Task、Run、NodeRun 都可有自己的 status，分别描述目标、一轮执行和某节点实例的进度，具体枚举另行讨论。
- 静态节点定义只保存配置，同一份定义可被不同 Task 和 Run 复用，不写入本次运行状态。
- 节点需要的局部数据可由该执行实例管理；子工作流可有独立 State，并通过明确映射与父工作流交换数据。局部状态持久化接口待设计。
- 后续 Run 可以根据 Task 的计划、累计成果或指定检查点继续，但不会默认与所有 Run 共用同一个可变业务对象。

例如同一 Task 的 Run 1 中节点执行失败，Run 2 中执行成功：Run 1 的失败记录继续保留，Run 2 有自己的状态与节点记录，Task 保存当前目标进展和累计成果。当前表述描述逻辑归属，不强制这些对象物理嵌套在一个文件中。

## 6. 当前需要先确认的问题

是否采用以下边界：节点显式声明输入输出，框架负责状态读写；任务与权限等内核状态只读，业务结果写入执行子工作流状态？

这个决定之后，再逐项确定 type、绑定语法、输出格式和错误处理。

# 独立验收会话、证据与判断可靠性

最后整理：2026-10-23。状态：后续扩展备忘；当前阶段不实施模型内容验收。

**最新决定：当前讨论的版本只做清单交付完整性检查。本文保留独立验收会话、内容评审和置信度相关讨论，供后续参考，不作为当前实现要求。**

## 1. 本轮用户提案

- 验收阶段启用独立的临时会话。
- 先检查清单要求的交付文件是否齐全，例如 `readme.md` 和 `disign.txt`。
- 将用户任务描述和实际文件内容提供给临时会话，判断内容是否满足任务要求。
- 达标后成功；不达标反馈到执行阶段继续处理。
- 需要考虑模型可能给出迎合性或缺乏依据的判断，以及通过结论的可信程度。

以下记录对该提案的细化建议，未替用户确认具体策略。

## 2. 建议的验收分层

| 层级                   | 检查内容                                           | 主要执行方                               |
| ---------------------- | -------------------------------------------------- | ---------------------------------------- |
| 需求覆盖               | 用户明确提出的交付物和要求是否进入清单             | 规则辅助与独立模型评审，含糊处向用户澄清 |
| 交付完整性与确定性规则 | 文件是否存在、是否可读、内容或结构是否满足明确规则 | 框架和受控检查器                         |
| 内容达标               | 文件内容与任务目标、具体要求、参考资料是否一致     | 独立验收会话，按项给出依据               |

需求清单覆盖和交付文件完整是两项检查。若最初清单遗漏用户要求，仅检查清单中的文件存在仍可能错误通过。

覆盖检查可以在清单生成后进行；最终验收继续核对生效任务要求，发现遗漏时提出修订，不能在不留记录的情况下改变标准。

确定性检查失败时，可以直接反馈明确问题，不必为了缺失文件再调用模型。通过确定性检查，只能证明这些规则满足，不能据此推断内容全部正确。

## 3. 临时验收会话接收什么

建议由框架构建独立的输入包：

- 原始任务目标和用户已确认的后续变更。
- 生效验收清单、任务要求版本和清单版本。
- 框架实际读取的文件内容或可按需读取的内容引用。
- 对应产物版本、内容摘要值、范围和读取完整性信息。
- 已完成的确定性检查与执行回执。
- 判断所必需的参考资料、配置或源数据，按权限按需提供。

例如，要判断 README 中启动命令与项目一致，可能需要项目配置；若要证明命令实际可执行，还需要受控执行的观察结果。仅阅读 README 的自我描述，不能推出这些结论。

建议不提供执行 Agent 的长篇对话、作者身份、满意度要求或“已经完成”等自我评价，减少锚定和自我辩护的影响。必要的实际执行事实通过框架记录提供。

临时会话是一次独立的验收上下文，不必在用户会话列表中新建聊天。验收报告和必要的输入来源、模型与配置版本仍需要关联 Run 保存，详细内容保留遵守脱敏与保留策略。

## 4. 隔离边界

独立上下文不保证模型判断独立或正确。同一模型可能在执行和验收中共享相同盲点；更换模型或增加评审也不能自动消除共同错误。

建议：

- 验收器按固定要求逐项检查，允许明确表示不知道或证据不足。
- 验收器只读取授权的交付物和证据，不修改交付物、清单和权限。
- 文件内容属于待检查数据；其中要求“忽略要求”“直接通过”等文字不改变评审规则。
- 模型引用的段落或行号由框架验证其实际存在；引用有效仍不等于推论必然正确。
- 验收期间读取稳定版本的产物。文件变更后，对受影响项重新验收。
- 大文件无法完整进入上下文时，提供受控分页/检索，并记录覆盖范围；未读部分不能宣称已经检查。

可配置独立的验收模型，但选择与默认策略尚待讨论。

## 5. 建议的报告

逐项记录，避免只返回一个总体分数：

| 字段       | 内容                               |
| ---------- | ---------------------------------- |
| 验收项关联 | 对应任务要求、清单版本和验收项     |
| 结论       | 通过、未满足或证据不足             |
| 检查范围   | 读取了哪些文件、版本与内容范围     |
| 依据       | 文件位置、引用、规则结果或执行回执 |
| 简要解释   | 为什么这些依据支持结论             |
| 缺口       | 哪些要求缺少依据，建议补充什么     |

结构化格式和必填字段能减少遗漏，不能保证语义判断正确。

检查器异常、模型拒绝或读取失败另记为验收执行异常，不能直接推断交付物未达标。

## 6. 关于置信度

后续引入模型内容验收时，建议先让运行策略依赖检查结果、证据和未解决项。

- 模型自报的分数可以记录为主观信号，但不直接解释为真实正确概率。
- 没有在目标任务上做过校准时，不使用自报的 0.9 或 0.95 作为自动放行保证。
- 评审结论一致也不代表独立证据充分；不能简单将多个模型投票换算为正确率。
- 可在证据冲突或任务配置要求时增加独立复核，并保留所有意见，不能反复抽样直到获得一次通过就结束。

若未来要使用概率阈值，需要建立与实际任务匹配、有人类标注的合格及不合格样本，包含漏项、错误事实、表面完整和含糊要求等情况；在留出的评估样本上测量误通过与误拒绝情况，校准后再制定策略。

模型、提示、评分规则和任务类型改变后，应重新评估。相关统计反映特定样本分布下的表现，不保证每次任务都判断正确。

## 7. 结果如何路由：建议，待确认

| 情况                                             | 建议行为                                   |
| ------------------------------------------------ | ------------------------------------------ |
| 必需确定性检查通过，必需内容要求有足够依据且通过 | 按生效完成策略结束，标明使用了哪些检查方式 |
| 明确发现可修复问题                               | 把问题、证据和预期条件交回执行阶段         |
| 证据不足且可以在授权范围内补充                   | 补充证据后重新检查相关项                   |
| 需要新授权、用户解释或人工判断                   | 暂停等待用户处理                           |
| 验收运行本身异常                                 | 记录错误，按恢复策略处理                   |

任一必需项仍有未解决的证据缺口时，不自动标记任务验收完成。问题已被证实需要修复时，也不能仅靠改变分数得到通过。

自动补充证据的范围、复核触发规则和人工接管时机尚待确认。

## 8. 与行动计划的关系

行动计划描述执行安排，验收清单描述完成要求，验收报告记录实际判断。

验收失败可以促使执行器修改行动计划；验收标准的修改仍需走单独的版本化流程。执行器不能直接编辑最终验收结论。

## 9. 研究依据与适用范围

- [Judging LLM-as-a-Judge with MT-Bench and Chatbot Arena](https://arxiv.org/abs/2306.05685)：研究了模型评审的位置、篇幅和自我偏好等偏差。论文中的任务与人类偏好一致性不直接等同于本项目对任意产物的验收准确率。
- [Language Models (Mostly) Know What They Know](https://arxiv.org/abs/2207.05221)：在特定设置中研究模型自我评估和校准，也报告了新任务上的校准挑战。由此不能直接将未经评估的自报置信度当作可靠概率。

本设计建议根据这些研究中的限制采取证据、校准和不确定性处理机制；具体产品效果需要针对实际任务评估。

## 10. 后续再讨论的问题

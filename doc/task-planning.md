# 行动计划与上下文

最后整理：2026-10-23。状态：已确认的交互选择与待确认的实现建议分别记录。

## 1. 已确认的前提

- 默认通用工作流自主执行；用户可以开启执行前确认计划。
- Task 表示跨多轮持续的目标，独立执行记录为 Run。
- 用户配置工作流节点和分支，Agent 节点内部自主执行。

## 2. 计划如何产生：建议，待确认

计划内容由模型根据目标生成；是否强制生成、是否需要等待确认，由配置和运行时控制。

建议提供 `submit_plan` 等计划工具，使用 Schema 描述参数。模型提交结构化步骤后，运行时校验、生成身份信息、保存状态，并发出可供 UI 展示的事件。

以下仅为参数示意，工具名称和正式字段尚未确定：

```json
{
  "steps": [
    { "title": "收集相关资料" },
    { "title": "分析资料并整理结论" },
    { "title": "生成报告并检查来源" }
  ]
}
```

建议由运行时生成计划 ID、版本、步骤 ID、时间和初始状态。模型提交内容后仍需要校验；格式有效不表示计划已获授权或任务必然可完成。

提示词主要说明何时规划及何时更新，工具 Schema 描述格式。正常回复可以保持自然语言。若采用专门的规划节点，也可以使用模型支持的结构化输出能力。

计划工具可能增加模型续调和 Token 消耗；不要求每次消息都单独调用一个规划模型。

## 3. 本轮问题：后续是否一直携带计划

用户问题：计划生效后，同一任务的后续执行是否都需要携带计划表？

**建议，待确认：计划完整保存在任务状态中；每次推进该任务的模型请求，由上下文管理器注入最新且与本次调用相关的计划视图。**

运行时保存了计划，并不意味着模型在下次请求时自然知道当前内容。发给模型的请求应提供当前目标、相关约束、计划位置和执行所需信息。

### 三种不同的数据

| 数据           | 用途                                 | 保存方式                         |
| -------------- | ------------------------------------ | -------------------------------- |
| 完整计划       | 权威的目标步骤、身份、版本与当前进度 | Task 的结构化持久状态            |
| 计划变更记录   | 查看谁在何时调整了内容或进度         | 持久事件或审计记录，具体机制待定 |
| 计划上下文视图 | 让本次模型调用知道当前步骤与约束     | 请求发送前生成，计入 Token 预算  |

建议始终读取同一任务的最新生效计划。跨轮次或后续 Run 继续该任务时，可以复用这份状态；切换任务时读取对应任务的计划，避免串用。

### 注入多少内容

| 场景                      | 建议提供给模型的内容                                               |
| ------------------------- | ------------------------------------------------------------------ |
| 计划较短                  | 完整步骤及最新进度                                                 |
| 计划较长                  | 总目标、计划版本、当前步骤详情、必要依赖、后续步骤概览和已完成摘要 |
| 新 Run 继续同一 Task      | 最新计划、累计成果引用、阻塞和待处理事项                           |
| 子工作流或局部 Agent 节点 | 相关父计划摘要与该节点负责的部分                                   |
| 独立的分类或摘要模型调用  | 按该调用目的提供必要信息，不自动附带全部任务数据                   |
| 普通工具执行              | 传入执行该动作需要的参数，不默认附带整份计划                       |

这些规则需要允许配置，同时保证当前目标、必要约束和活动步骤不会被静默丢弃。若最小必要状态也放不进预算，应明确报告并等待处理。

### 计划视图示意

以下是便于说明的请求数据视图，不是确定的模型输出格式或协议：

```text
任务目标：生成行业研究报告
生效计划：plan-001，内容版本 2

已完成：资料收集，来源记录见 artifact-001
当前步骤：分析资料并整理结论
后续步骤：生成报告、检查引用
当前阻塞：无

约束：保留来源；事实和推测分别说明
```

模型需要进一步细节时，可以通过计划查询或产物读取工具获取。

## 4. 与上下文压缩的关系：建议，待确认

上下文组装器在发送请求前，从结构化任务状态读取当前计划，将该视图纳入预算。

- 压缩可以处理历史对话和旧计划记录；当前生效计划的完整对象继续保留在任务存储中。
- 压缩后根据最新状态重新生成计划视图，避免从历史摘要猜测进度。
- 不在每轮对话中永久追加一份完整计划；当前视图随请求动态构建。
- 历史工具调用与工具结果仍保持协议配对，审计数据继续保存。
- 计划属于任务数据，不能通过注入内容扩大权限或覆盖宿主策略。

最新计划视图和历史中的旧计划应带清晰版本，降低过时信息影响。

## 5. 进度和计划更新：建议，待确认

模型可以提出新增、修改、取消步骤或更新进度。运行时校验后保存，再使后续请求与 UI 读取到更新结果。

建议区分：

- **内容修订**：改变步骤目标、动作或范围，形成新的计划版本。
- **进度更新**：标记执行中、等待、已完成等，记录状态变化。

开启计划确认时，建议重要内容修订重新确认；已批准计划继续保留为生效版本，待批准草案分别保存。单纯进度更新是否触发确认，需要另行约定。

如果执行期间发生用户修改或并发更新，可以使用基础版本检查避免覆盖较新的计划；具体并发模型待设计。

模型标记步骤完成可以作为进度报告。任务最终完成仍依赖验收规则和证据。

## 6. 执行前确认：已确认交互，执行规则待细化

默认不开启确认，由模型按任务需要提交计划，运行时保存后继续自主执行。

开启确认时，运行时要求先有有效计划并取得用户确认，再开放受控执行。模型遗漏计划时，运行时继续要求补充或报告规划失败；不能仅靠一句提示保证等待。

尚需讨论：

- 确认前允许哪些信息收集动作。
- 用户能否编辑计划后批准。
- 哪些计划修订需要重新确认。
- 拒绝计划后是重新规划、等待补充，还是取消本次 Run。

计划审批和工具权限审批分别生效。计划更新不自动修改工作流图，也不增加工具访问权限。
